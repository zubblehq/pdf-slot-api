# @pdf-slot/core

The maths that decides where every character goes on the page: text wrapping,
glyph positions, PDF coordinates, table geometry, and the renderer itself.

## Why this package exists separately

Two programs run this code. The browser runs it to draw the preview the user
positions text with; the server runs it to produce the PDF. **Same code,
called twice — and that is the only reason the preview matches the downloaded
file.**

That promise is the product. If the two sides ever run different versions of
this package, the preview and the download disagree, and they do it silently:
no error, just text slightly out of place, found by a customer.

So this is one package with one source, consumed by both, and **the two
consumers must be pinned to the same commit.** Not a compatible range — the
same commit. A range like `^1.4.0` lets two projects resolve to different
versions while both look correct, which is precisely the failure this
arrangement exists to prevent.

```json
"@pdf-slot/core": "github:zubblehq/pdf-core#7f3a901"
```

A check that those two lines match belongs in CI. A runtime check that the
browser and the server report the same version belongs in the service — the
first catches a mistake at build time, the second catches a half-finished
deploy.

## It ships as TypeScript, on purpose

There is no build step and no `dist`. `main` points at `src/index.ts`.

This looks like an oversight and is not. Both consumers compile TypeScript
themselves as part of their own build, so compiling here would mean
maintaining a build, a published artifact and a release step to produce
something neither of them needs. Verified rather than assumed:

- **bun** runs these modules directly from `node_modules` and returns correct
  results.
- **Vite 8** transforms them as part of a normal production build.

The consequence worth knowing: a consumer whose bundler cannot read TypeScript
would need a build adding here first. If that ever happens, add `tsc`, point
`main` and `exports` at `dist`, and nothing else about this package changes.

## The font files

`src/fonts/files/*.ttf` are not read at runtime. `src/fonts/registry.ts` holds
only their *names*; the bytes arrive one of two ways:

- the browser fetches them from its own `public/fonts/`, so that the bytes it
  draws with and the bytes it embeds are one download;
- the server imports `./fonts/embedded`, which is those same files as base64,
  generated by `scripts/embed-fonts.mjs`.

The TTFs are kept here because they are the source for that generated module
and for the tests that check glyph positions. Regenerate with
`npm run fonts:embed` after changing anything in `files/`.

## Tests

170 of them, and they are the reason this package can be changed safely. The
ones that matter most build a real PDF, read the glyph coordinates back out of
its content stream, and compare them against what `layoutText` predicted —
`test/invariant.test.ts`. If that fails, the preview no longer matches the
download, whatever else passes.

```
npm test
```
